# Quality Guard (ISO9001:2015 & Physical 5S)

「言葉だけの品質と5Sを排し、物理的な確認コマンドの実行と自動消去ゲートによって環境の清潔を強制する」

## 1. 物理的 PDCA ゲート (The PDCA Gate)

🟡中（既存コード修正）以上のすべてのタスクにおいて、以下の物理ゲートをステップごとに強制します。

*   **Plan (リスク判定ゲート)**:
    作業開始前に `git diff --stat` 等で既存コードとの変更差分を分析し、**必ず `quality/risks.md`（リスク・影響分析シート）を物理的に作成・追記（`write_to_file`）しなければ、実際のファイル修正を一切開始してはなりません。**
    - 🟢 **低 (Low)**: 新規ファイル/テスト/ドキュメントのみ。2ファイル/20行以下。
    - 🟡 **中 (Mid)**: 既存コード修正。5ファイル/100行以下。
    - 🟠 **高 (High)**: API/外部連携変更、構造変化。10ファイル/300行以下。
    - 🔴 **極 (Ultra)**: DB変更/本番設定。300行超。
*   **Do (実装ゲート)**:
    `task-tdd-expert` に従い、TDDサイクルを実行。
*   **Check (3層検証ゲート)**:
    単体テスト -> 統合/E2Eテスト -> 本番相当テスト を順次実行。検証結果をログに明確に記録。
*   **Act (不適合管理ゲート)**:
    テスト・ビルド不適合（エラー）を解決した場合、その根本原因と是正措置を `tasks/` および [self-evolution](../self-evolution/SKILL.md) スキルの `references/pattern-catalog.md` に**物理的に書き出し（追記）**を完了するまで、タスク完了としてはなりません。

## 2. 物理5Sとリソース監視（機械的クリーンアップコマンドの強制）

抽象的なコンセプトとしての5Sやお題目のリソース監視を廃し、作業ツリーとリソースを健全に保つための「物理コマンドの実行」をステップに義務付けます。

### ① 【作業開始前のツリー整頓 (整理・整頓の物理的解決)】
- **ルール**: 🟡中（既存コード修正）以上のすべてのタスクを開始する前に、**必ず `git status` を実行**し、現在の作業ツリーが完全にクリーンである（未追跡のゴミファイルや中途半端な修正コードが存在しない）ことを確認します。
- **代替手法**: 未追跡の不要なテンポラリファイルが存在する場合、必ず `git clean -fd` または `rm -rf` / `Remove-Item` コマンドを実行して作業ツリーを完全なクリーン状態にしてからタスクを開始します。

### ② 【大規模処理前後のリソース監視 (リソース管理の物理的解決)】
- **ルール**: Polarsによる数百万行以上のデータ処理、大規模テストスイートの実行、またはプロダクションビルドを実行する**「直前」**と**「直後」**に、**必ず以下のリソース確認コマンドを実行し、結果（CPU/メモリ使用率）をログに記録**しなければなりません。
- **実行コマンド**:
  - Linux: `ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head -n 6` および `free -m`
  - Windows: `Get-Process | Sort-Object CPU -Descending | Select-Object -First 5` および `Get-Counter '\Memory\Available MBytes'`

### ③ 【タスク完了時のデバッグ物完全消去 (清掃・清潔の物理的解決)】
- **ルール**: タスクを完了してユーザーに完了報告を送信する直前の「最終ステップ」として、**必ず `git status` を実行し、開発中に自ら作成した一時的なテスト用スクリプト、デバッグログ、中間データファイルを特定の上、物理削除コマンド（`rm -f` / `Remove-Item -Force` 等）で完全に消去**しなければなりません。
- **「なぜそうしたか」の論理的根拠**: 不要なゴミファイルを作業ツリーやスキル内に残存させると、将来的に他のタスクが実行される際のノイズ（不整合）となり、別の未定義バグやコンテキストの混入を引き起こす原因になるためです。
