# Task & TDD Expert (Workflow)

## 1. 実装前Web検索物理ゲート (The Web-Search Gate)

具体的なコード（ライブラリの使い方、CSS/HTML設計、API実装、アルゴリズム）の作成や仕様決定を開始する前に、**必ず以下の「Web検索ゲート」を通過しなければなりません。**

- **物理ツールの実行**: 
  コードを変更する前に、必ず `search_web` ツールを実行し、実装しようとしている技術、ライブラリ、API、またはCSS仕様 of「最新のベストプラクティス」「公式ドキュメント」「既存 of 優れた解決策」を最低1回（推奨は複数回）検索・精読します。
- **タスクファイルへの証拠記録（Evidence）**: 
  検索した結果、得られた「1. 使用した検索クエリ」「2. 参照した主要な公式ドキュメントのURL」「3. 採用する具体的なベストプラクティス（知見）」を、作成するタスクファイル `tasks/YYYYMMDD_TXXX_タスク名.md` の「背景・アプローチ」に物理的に書き出さなければ、実際のコード編集（`write_to_file` / `replace_file_content` 等）を一切開始してはなりません。

*   **「なぜそうしたか」の論理的根拠**: 
    AIの脳内にある知識（事前学習データ）のみに依存して具体的なコードを書くと、古いAPI仕様、非推奨の記法、非効率な車輪の再発明、または我流の不完全な実装（技術的負債）になりやすいためです。実装の直前に強制的に「検索ツールを呼び出し、URLと知見をタスクログに記録する」という物理ステップを挟むことで、常に世の中の最先端かつ検証済みの仕様に基づいた高品質な「具体性」を実装するためです。

## 2. タスク管理 & TDD
- **Task**: `tasks/YYYYMMDD_TXXX_タスク名.md` を作成し、上記「Web検索ゲート」の証拠、背景、目的、結果、次アクションを管理します。
- **TDD**: テストを先に作成（Redを確認）し、最小限の実装（Green）とリファクタリング。

## 3. GitHub Flow & Security
- 変更は feature ブランチ、PR 経由、1機能 1コミット。
- IPA準拠: 入力検証、スタックトレーレスポンス禁止、シークレット管理。

# エラープロトコル & 委譲方針

## 対処ルール
- コード・ファイルの変更およびエラー是正に際しては、専門スキル `hypothesis-driven-editor` をアクティベートし、物理的仮説ログゲートの書き出しと段階的アプローチ（Low to High）を厳格に実行します。
- 変更前の保存 (`git add`)、変更後の自己レビュー (`git diff`)。

## サブエージェント (Subagent)
- 独立調査 3つ以上、重い検索・探索、長時間処理は `generalist` へ委譲。
