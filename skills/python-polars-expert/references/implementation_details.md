# Python & Polars Expert (Implementation Specifications)

## 1. 静的コード品質ルール (Static Quality Rules)

AIが「綺麗で堅牢なコード」を感覚的に書くのを防ぐため、以下の静的検証可能な制約を強制します。

### ① 【関数設計の数値制限（高凝集・低結合の物理的解決）】
- **引数の数**: 1つの関数・メソッドの引数は、デフォルト値を持つものを含めて**最大4個まで**とします。これを超える場合は、データ格納用クラス（`dataclass` や `pydantic.BaseModel`）にデータを統合して引き渡さなければなりません。
- **ネストの深さ**: `if`, `for`, `while`, `try-except` などの制御フローのネストは、**最大2階層まで**とします。3階層以上のネストが発生する兆候が見えた場合、必ず別関数に処理を抽出し、フラットなデータ構造で受け渡します。
- **「なぜそうしたか」の論理的根拠**: 引数の多すぎる関数や、深いネストを持つ関数は、テストケースが爆発的に増加し、バグの温床となるためです。これを静的数値で制限することで、機械的にシンプルな単一責任のモジュール構造を維持させます。

### ② 【自明コメントの完全排除と「動機ログ」の義務化】
- **自明なコメントの禁止**: 「Aに1を加算する」や「リストをループする」といった、コードを読めば自明な説明的コメントを一切禁止します。
- **「なぜそうしたか（動機・理由）」の記述**: コメントや docstring を書く場合は、処理内容（What）ではなく、**「なぜそのアルゴリズムを採用したか」「なぜその仕様を実装したか」の論理的根拠（Why）のみ**を記述します。
- **「なぜそうしたか」の論理的根拠**: コードそのものが最大のドキュメントであり、自明なコメントはノイズとなって可読性を損ねるためです。一方で、設計上の「意図や背景（Why）」はコードから自動抽出できないため、未来のデバッガーのために明文化しておく必要があります。

### ③ 【ロギングの機械的一元化】
- **ルール**: 標準出力（`print`）をデバッグ目的以外で直接使用することを禁止します。
- **初期化方法**: 各モジュールで必ず以下のように `logging` インスタンスを取得し、一元的なログ出力を行います。
  ```python
  import logging
  
  logger = logging.getLogger(__name__)
  ```
- **「なぜそうしたか」の論理的根拠**: 出力先（コンソール、ファイル、クラウド監視など）やログレベル（DEBUG/INFO/ERROR）の制御を、ソースコードを変更することなく外部設定から一元制御できるようにするためです。

### ④ 【uv による決定論的実行】
- パッケージ追加: `uv pip install <package>`（またはプロジェクト環境では `uv add <package>`）
- 実行: 必ず `uv run python <script.py>`
- 仮想環境: `uv venv` で作成し、常に有効化

## 2. データ処理 (Polars / xlwings)

- **読込**: Excel読込は `pl.read_excel` (Polars)
  ```python
  import polars as pl
  
  df = pl.read_excel(path, read_options={"header_row": 0}, infer_schema_length=0)
  ```
- **Polars 1.0.0+ 掟**:
  - **`replace` の `default` 引数使用を完全禁止**:
    - 非推奨警告：`DeprecationWarning: the 'default' parameter for 'replace' is deprecated.`
  - **`replace_strict` の強制**:
    - 値の置換にデフォルト値を設定する場合は、必ず `.replace_strict(mapping, default=value)` を使用します。
- **Excel編集**: セルごとの書き換えが必要な場合は `xlwings` を使用し、Polarsで処理した大容量データの一括流し込みと書式設定のみを担当させます。

## 3. GUI 開発 (ttkbootstrap)

- **配置**: 必ず `grid(padx=10, pady=10)` などのグリッドレイアウトを使用し、各ウィジェットに適切なパディングを設定して画面の視認性を高めます。
- **サイズ制御**: `geometry()` によるウィンドウサイズのハードコード（静的固定）を完全禁止します。ウィジェットの伸縮（`rowconfigure`, `columnconfigure`）とパディングによって自動調整されるように設計します。
- **「なぜそうしたか」の論理的根拠**: 異なる解像度やスケーリング（高DPI環境）において、レイアウトが崩れたり、文字がはみ出したりするのを動的に防止するためです。

## 4. Google SDK 掟

- **使用API**: 必ず `google.genai` (Google GenAI SDK) を使用し、古い `google.generativeai` (legacy SDK) は完全に使用禁止とします。
