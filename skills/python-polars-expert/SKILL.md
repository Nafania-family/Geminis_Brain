# Python & Polars Expert (Logic-Driven)

「抽象的なSOLID/KISS原則を排し、物理的なコード品質ゲートと静的機械ルールによって堅牢なPython実装を強制する」

## 1. 物理的コード品質ゲート (The Code Quality Gate)

Pythonのスクリプト、モジュール、またはクラスを作成・変更する際、ファイルを実際に修正・保存（ツール呼び出し）する前、または直後の検証時に、**必ず `tasks/python_quality_validation.md`（または該当検証ログ）に以下のチェックリストを物理的に書き出し、すべて適合（PASS）していることを証明しなければなりません。**

### 【Python コード品質検証シート】
```markdown
# [検証中] Python コード品質検証シート

- **対象モジュール/関数**: （どの処理を修正・作成するか）
- **静的チェックリスト**:
  1. [ ] 新規・修正されたすべての関数が、コメントを除いて最大30行以内に収まっているか？ (PASS / FAIL)
  2. [ ] Polarsの処理において、pandasライクな中間DataFrame代入がなく、メソッドチェーン（遅延評価）で一括記述されているか？ (PASS / FAIL)
  3. [ ] 新規・修正されたすべての関数に、引数・戻り値の型ヒントが100%付与されているか？ (PASS / FAIL)
  4. [ ] パッケージ管理や実行において、pipやvenvを直接叩かず、すべてuvコマンドのみを使用しているか？ (PASS / FAIL)
- **なぜこの設計にしたか (Rationale)**:
  - 複雑な処理をどのように小さな単一責任の関数に分割したか、またはPolarsのクエリ最適化をどのように活用したかの論理的根拠。
```

## 2. 4つの静的Python/Polars鉄則（機械的ルール）

AIの「綺麗に書こうとする意識」に依存するのをやめ、コード生成時に以下のルールを「静的検証可能な制約」として完全に強制します。

### ① 【1関数の30行制限（単一責任・KISS原則の具現化）】
- **ルール**: docstringやコメント、空行を除き、**1つの関数またはメソッドは「最大30行」以内**に収めなければなりません。
- **「なぜそうしたか」の論理的根拠**: これを超える関数は、ほぼ確実に「複数の責任（入力検証、変換、出力、エラー処理等）」を同時に抱え込んでおり、テストや再利用性を著しく困難にするためです。30行を超える兆候が見えたら、即座に関数を役割（サブプロセス）ごとに分割し、論理的なデータ受け渡しインタフェースを構築します。

### ② 【Polars pandas-like代入禁止＆Lazyチェーン強制ルール】
- **ルール**: pandasのように「DataFrameを中間変数に何度も代入して順次書き換える」処理を禁止します。また、特別な理由（即時メモリロードが必要等）がない限り、データの読み込みは `scan_csv` / `scan_parquet` 等による遅延評価から開始することを義務付けます。
- **代替手法**: `pl.LazyFrame` に対する明確なメソッドチェーン（例: `lf.filter(...).with_columns(...).select(...)` 等）を用いて処理を一気通貫で記述し、最終段階でのみ `.collect()` を呼び出して結果を展開します。
- **「なぜそうしたか」の論理的根拠**: Polarsのクエリプランナー（最適化エンジン）がクエリ全体（フィルタープッシュダウンやプロジェクションプッシュダウン等）を最も効率的な順序で並べ替えて実行できるようにし、メモリ消費量と実行時間を極小化するためです。

### ③ 【型ヒント(Type Hints)の100%義務化】
- **ルール**: 新規に作成・または修正するすべての関数・メソッドの引数（引数名およびコロン）と戻り値（`->`）には、**必ず Python の型ヒントを100%付与**しなければなりません。
- **代替手法**: 単純な型（`str`, `int`）だけでなく、複雑なデータ構造は `list[str]`, `dict[str, Any]`、Polars固有のオブジェクトは `pl.LazyFrame`, `pl.DataFrame` などを明記します。型エスケープである `Any` は、真にデータ構造が未定の場合を除いて原則禁止とします。

### ④ 【uvによる一元的な環境・パッケージ管理】
- **ルール**: グローバルな `pip` や Python 標準の `python -m venv` を直接呼び出すことを一切禁止します。
- **代替手法**: パッケージ追加は必ず `uv pip install`、実行は `uv run`、仮想環境作成は `uv venv`、初期化は `uv init` のみを使用することを義務付けます。
- **「なぜそうしたか」の論理的根拠**: 異なるプロジェクト間での依存関係の競合を完全に排除し、極めて高速かつ決定論的な（常に同じパッケージバージョンがインストールされる）開発環境を維持するためです。
