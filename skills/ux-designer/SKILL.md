# UX Designer (Apple HIG + Logic-Driven)

「感覚やスローガンによるデザインを排し、物理ゲートと静的機械ルールによって premium UI を強制する」

## 1. 物理的デザイン検証ゲート (The UI/UX Gate)

UIコンポーネント、HTML、CSS、またはフロントエンドページを作成・変更する際、ファイルを実際に修正・保存（ツール呼び出し）する前、または直後の検証時に、**必ず `tasks/ui_design_validation.md`（または該当検証ログ）に以下のチェックリストを物理的に書き出し、すべて適合（PASS）していることを証明しなければなりません。**

### 【UI/UXデザイン検証シート】
```markdown
# [検証中] UI/UX デザイン検証シート

- **対象UIコンポーネント/画面**: （どのUIを修正・作成するか）
- **静的チェックリスト**:
  1. [ ] カラー、フォント、余白にプレーンな直書き（#fff, 16px, 10px等）がなく、すべて CSS 変数（design-tokens.css）に置き換わっているか？ (PASS / FAIL)
  2. [ ] インタラクティブな全要素に `aria-label` 等のアクセシビリティ記述が含まれているか？ (PASS / FAIL)
  3. [ ] ボタン押下後やデータ読み込み中のローディング表示（disabled + スピナー等）が実装されているか？ (PASS / FAIL)
  4. [ ] 破壊的操作（削除等）に赤系統カラー適用と、物理的な確認ダイアログ（または二重チェック）が実装されているか？ (PASS / FAIL)
- **デザインの心理学的根拠 (Rationale)**:
  - どの心理学法則（段階的開示、目標勾配、認知負荷の低減等）を**具体的にどのようなUI要素として具現化**したか？（「〜に基づいて設計した」ではなく「プログレスバーを設置して目標勾配効果を持たせた」のように物理的に記載）
```

## 2. 4つの静的UI/UX鉄則（機械的ルール）

AIの自律的な理解力やお題目の順守に期待するのをやめ、コード生成時に以下のルールを「静的検証可能な制約」として完全に強制します。

### ① 【100% CSS変数強制ルール】
- **ルール**: CSS（または Tailwind、インラインスタイル等）におけるカラーコード（`#ffffff`, `rgb(...)` 等）、フォントサイズ（`14px` 等）、余白・パディング（`10px`, `1rem` 等）、角丸（`4px` 等）の**プレーンな生値の直書きを完全に禁止**します。
- **代替手法**: 必ず [design-tokens.css](references/resources/design-tokens.css) に定義されている変数（例: `--color-primary`, `--spacing-md`, `--font-size-base`, `--radius-lg` 等）のみを使用します。

### ② 【ARIAアクセシビリティ100%必須ルール】
- **ルール**: スクリーンリーダーを使用するユーザーおよびブラウザテストに明確なコンテキストを伝えるため、すべての `button`, `input`, `select`, `textarea`, `a` 要素には、**`aria-label`、`aria-describedby`、または明確に目的に直結するテキストコンテンツを物理的に配置することを義務付け**ます。また、主要なセクションは `<header>`, `<main>`, `<footer>`, `<nav>`, `<section>` などのセマンティックHTML5タグのみで構成します。

### ③ 【非同期・ローディング表示のガード強制ルール】
- **ルール**: データをAPI等から読み込む（または非同期処理を待つ）、あるいはフォームやボタンを送信した後の「すべての待機状態」に対して、**スピナー、スケルトンスクリーン、またはプログレスバーによる視覚的な進捗の表示**と、送信ボタン等の **`disabled` 属性化**を同時に実装しなければなりません。
- **「なぜそうしたか」の論理的根拠**: ロード中の無応答状態（ユーザーがボタンを連打してしまう等）によるバグや認知負荷を防ぐためです（「目標勾配効果」「決断疲れの回避」の物理的解決）。

### ④ 【破壊的操作の二重確認ガード強制ルール】
- **ルール**: データの削除や、元に戻せない破壊的な処理を行うすべてのUI（削除ボタン、リセットボタン等）は、必ず**赤系統のカラー変数（`--color-danger` 等）を割り当てること**、かつ処理実行前に**「確認モーダルダイアログ」または「物理的なチェックボックス（『本当に削除します』等）による二重チェック」のガードを必ず実装すること**を義務付けます。
- **「なぜそうしたか」の論理的根拠**: 人間の誤操作による不可逆なデータ損失を、UI設計の仕組み（ガード）によって物理的に防止するためです（「損失回避」の物理的解決）。
