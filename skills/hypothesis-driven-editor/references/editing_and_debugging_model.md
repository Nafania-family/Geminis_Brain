# 仮説検証型エディター＆デバッグモデル (Hypothesis-Driven Editor) 詳細

AIエージェントが「ルールを認知していても、実際のコード作成・編集・修正時にそれを無視して思いつきで編集する」という実効性の低さを克服するため、**「物理的なツール呼び出し前のアクション制限」**を組み込んだ編集・デバッグプロトコルです。

---

## 1. 物理的仮説・方針ログゲート (The Hypothesis & Plan Gate)

AIがファイル編集・新規作成・リファクタリング・バグ修正を行う際、コード編集ツール（`replace_file_content` や `write_to_file` 等）を呼び出す前に、**必ず `tasks/hypothesis_log.md`（またはタスクディレクトリ内の該当ログファイル）に以下の内容を書き出すこと（物理的にファイル作成・追記）を、コード変更の「絶対的な前提条件（ゲート）」とします。**

### 【仮説・方針ログテンプレート】
```markdown
# [検証・適用中] 編集・仮説ログ (Layer: 🟢/🟡/🟠)

- **目的/現状の課題**: （新規実装・リファクタリング・エラーメッセージ等、具体的な目的）
- **対象レイヤー**: （🟢レイヤー1 / 🟡レイヤー2 / 🟠レイヤー3）
- **IF (変更内容)**: （どのファイルをどう変更するか）
- **THEN (期待される変化・結果)**: （ビルド/テスト通過、期待通りの挙動、特定の状態変化など客観的な検証基準）
```

*   **「なぜそうしたか」の論理的根拠**: 思考プロセス（Thinking）内だけの検討では、直前のアクションや慣性に流されて根拠の薄い編集に走りやすくなります。コード変更の前に「ログファイルを新規作成・追記する」という**物理的な外部ツールの呼び出しを挟むことで、強制的に自身の思考を論理モデルにロックインさせるため**です。

---

## 2. 段階的アプローチ (Low to High)

変更や修正を行う際、AIの思いつきに任せるのではなく、以下の「3つのレイヤー」の手順に従って段階的に探索・実装・検証を行います。

### 【探索・開発の3レイヤー】
*   **🟢 レイヤー1 (Low / 局所的・表層的)**
    *   *対象*: 単一ファイルの小規模変更、タイポ修正、局所的なロジック追加、型定義調整、依存関係の確認。
    *   *行動*: まず最初に、最も影響範囲の小さい局所的変更・検証で目的が達せられないかを評価・実施します。
*   **🟡 レイヤー2 (Mid / データフロー・モジュール間)**
    *   *対象*: 複数ファイルにまたがるインタフェース調整、モジュール間のデータ受け渡し、非同期処理の同期、状態管理の変更。
    *   *行動*: レイヤー1の局所的なアプローチで不十分な場合、データフローやモジュール間連携に焦点を当てて変更方針を立てて検証します。
*   **🟠 レイヤー3 (High / 構造・アーキテクチャ)**
    *   *対象*: モジュール全体の再設計、アーキテクチャの変更、DBスキーマ変更、新規枠組みの導入。
    *   *行動*: レイヤー1および2での検討・検証を経て、上位構造の変更が不可欠であると論理的・実証的に確認された場合にのみ大掛かりな変更を行います。

### ⚠️ レイヤー移行の絶対条件：段階的検証の徹底
- **大掛かりな変更前の局所検証**: 
  上位レイヤーへ無計画に飛躍するのではなく、局所的な最小単位での検証（プロトタイピング・単体テスト）を済ませてから構造的変更を行います。
- **「なぜそうしたか」の論理的根拠**: 
  影響範囲が大きい構造変更をいきなり行うと、失敗した際の原因特定が困難になり、広範囲なコードベースの汚染を引き起こすためです。

## 3. 失敗時の自動ロールバック・プロトコル (Clean Rollback)

編集適用後にビルドエラー、テスト失敗、またはTHENで定義した期待結果と異なる挙動が発生した場合、**直ちにコード変更ツール呼び出しをフリーズし、以下の手順を実行します。**

### 【物理ロールバック・アルゴリズム】
1. **即時停止**: 予期せぬエラーや不一致が発生した瞬間、追加のコード修正ツール呼び出しをストップします。
2. **ログ更新**: `tasks/hypothesis_log.md` に結果（不一致・失敗内容）を記録します。
3. **完全ロールバック**: `git checkout .` や `git restore` を実行し、試行した変更を1行残さず元に戻します。
4. **再評価**: 次のレイヤーまたは別の局所的方針について仮説・計画を立て直してから再度試行します。

*   **「なぜそうしたか」の論理的根拠**: 失敗したコードの上に継ぎはぎで修正（パッチワーク）を重ねると、問題の本質が見えなくなり副作用やバグの増殖を招くため、常にクリーンな状態を保つためです。

## 4. 記述・言語表現プロトコル (No Comparative Excuses)

仮説ログ、思考プロセス、変更理由、ユーザーへの報告を作成する際、以下の表現ルールを物理的な絶対制約とします。

- **比較・補足・受動表現の完全禁止**: 
  「〜のみならず」「〜にとどまらず」「〜だけでなく」「バグ修正時だけでなく」といった、過去の経緯や旧制約に依存した言い訳的・補足的な表現を禁止します。
- **第一義的・肯定的表現の義務化**: 
  仕様・プロトコル・目的を述べる際は、常に直接的かつ肯定的に記述します。
  - ❌ *「デバッグのみならずコード編集にも適用する」*
  - 🟢 *「コードおよびファイルの新規作成、編集、リファクタリング、デバッグを含むすべての変更操作において適用する」*
