## 2. 潜在的リスクと物理的防止策（なぜその設計にするか）

| リスク項目 | 発生原因 | 物理的防止策（設計上の根拠） |
| :--- | :--- | :--- |
| **1. 誤判定による必須SKILLの喪失** | 単一テストケースの偶然の通過や、例外発生時のファイル未復元 | 決定論的バリデータ（Schema, Regex, AST, Pytest）の全件評価に加え、複数回試行（安定性検証）をサポートする。またファイル操作は `try ... finally` とスナップショット退避により失敗時の即時100%ロールバックを強制する。 |
| **2. チャンク分割時の局所最適（分割境界問題）** | 前半50%と後半50%の双方に必須SKILLが分散している場合の探索停止 | 単純な二分探索を排し、Zeller の `ddmin`（分割数 $n=2 \to 4 \to 8 \dots |C|$ の動的粒度調整と補集合評価）を実装して数学的な 1-Minimality を保証する。 |
| **3. SKILLとHOOKの共依存による削除漏れ** | 特定フォーマットを指示するSKILLと、それをパースするHOOKを別々に抜くと両方FAILになる現象 | `group_id` によるバンドル単位のアブレーションと、本番推論テレメトリにおける HOOK 発火回数ゼロ（自然死）検知を組み合わせて共依存レガシーを一掃する。 |
| **4. 同一構成の重複評価によるAPIコスト浪費** | チャンク分割と個別検証の間で同一のSKILL組み合わせが再評価される | 有効コンポーネントIDの `frozenset` をキーとする決定論的評価メモ化キャッシュを導入し、同一構成に対する推論実行を1回に制限する。 |

## 3. 3層検証計画 (Check Gate)
1. **単体テスト (Unit)**: モデル優先度ソート、各種決定論的オラクル（JSON/Pydantic, Regex, Python AST, 関数実行）、HOOK自然死カウンタの境界値検証。
2. **統合テスト (Integration)**: 全消しショートカット、負の相互作用（邪魔なSKILL削除によるスコア向上）、共依存バンドル削除、`ddmin` と線形 `while True` の一致および評価回数圧縮（$O(\log N)$）の検証。
3. **本番相当E2Eテスト (E2E)**: 実際のディレクトリ上の `SKILL.md` ファイル群を対象としたトランザクション枝刈り・ロールバック、および Polars LazyFrame パイプラインによる監査レポート出力の完走検証。
